# 农业智能问答助手 · 面试问题集

> 按**被问到的概率**排序，分三档。每题给出：考察点、答题框架、追问预警。
> 数字和实现细节都来自项目实际代码与评测报告，可溯源。

---

## 使用说明

**别背答案，记框架。** 面试官能听出背稿子。每题记三个关键词，用自己的话串起来。

**三档的含义：**

| 档位 | 含义 | 策略 |
|---|---|---|
| A 档 | 几乎必问，答不好直接出局 | 必须能讲 2 分钟，有细节 |
| B 档 | 大概率会问，答好加分 | 能讲 1 分钟，说清取舍 |
| C 档 | 深挖时才会问 | 知道就答，不知道就说不了解 |

**一条硬规则：** 答不上来时，说「这块我当时没深入，我的理解是……」，比编一个答案安全。面试官追问两层就能听出真假。

## A 档 · 必问（7 题）

### A1. 介绍一下这个项目

**概率：99%** ｜ 开场第一题，决定后面问什么

**答题框架（90 秒）：**

1. **一句话定位**：一个面向农技咨询的本地知识库问答系统，用 RAG 解决通用大模型在农业领域知识不足、容易编造的问题。
2. **规模**：598 篇语料、85 万字，切成 2270 个片段，全部在本地跑，不需要服务器和显卡。
3. **链路**：语料抓取 → 清洗去重 → 中文断句切片 → 向量化入库 → 检索 top-5 → 拼提示词 → 生成回答，回答带来源引用。
4. **亮点**：在检索层做了混合重排，把 Recall@5 提到 88%；另外加了一层 Agent，让模型能调工具做多步推理。
5. **收尾**：整个系统单命令启动，前端六个页面，从知识库管理到历史记录都是完整的。

**追问预警：**
- 「598 篇哪来的」→ 从中国农业农村信息网抓的，三个栏目，清洗掉新闻稿后剩这些。
- 「为什么不用现成的产品」→ 通用模型答农技问题会编，而且引用不了原文。RAG 能把答案锚定在资料上。

---

### A2. 为什么要用 RAG，不直接微调模型？

**概率：95%** ｜ 这是 RAG 项目的第一道筛子

**答题框架：**

三个理由，按重要性排：

1. **知识更新**：农技资料每年都出新的（比如 2024 年的病虫害防控方案），微调一次成本高、周期长，RAG 换语料重建库就行，几分钟的事。
2. **可溯源**：农业建议是要落地的，用户得知道这话出自哪份文件。RAG 能返回来源片段，微调模型做不到。
3. **成本**：微调需要 GPU 和数据标注，我只有一台笔记本。RAG 的向量库是文件型的，CPU 就能跑。

**加分补充**：如果语料稳定、问题集中在固定类型，微调会更省推理成本。RAG 更适合知识频繁变化、需要引用的场景。

**追问预警：**
- 「那微调就没用了？」→ 不是。微调解决的是「说话风格和领域语感」，RAG 解决「事实从哪来」。两者可以叠加，但我这个场景知识更新快，优先 RAG。

---

### A3. 切片大小 500 / 重叠 50，怎么定的？

**概率：90%** ｜ 经典细节题，答不出说明没动手

**答题框架：**

1. **不是拍脑袋**：500 字大约是一个农技要点的完整长度——比如「越冬水怎么浇」这一段，从温度条件到浇后管理，正好 400–600 字。切太碎会丢上下文，切太大检索精度下降。
2. **重叠 50 的作用**：防止一句话被切断。中文没有空格，断点如果刚好落在句子中间，前半句和后半句分属两个片段，检索时可能只召回一半。
3. **断句策略**：优先在中文标点（。！？；）处切，其次逗号，最后才硬切。这样片段读起来是完整的段落，不是半截话。
4. **验证过**：切成 2270 个片段，平均每篇 3.8 个，没有出现大量超短片段（比如 20 字的碎片），说明参数是合适的。

**追问预警：**
- 「怎么验证 500 是对的？」→ 我没有做严格的 A/B 对比。判断依据是片段完整性和检索命中率——用 25 题测出 Recall@5 88%，如果切太碎这个数会明显下降。**（诚实说没做对比实验，比编一个「我试了 300/500/800」安全）**
- 「为什么不按段落切？」→ 段落长度差异太大，有的 50 字有的 2000 字，向量化后长段落的语义会被稀释。

### A4. 怎么防止模型胡说（幻觉）？

**概率：90%** ｜ RAG 的核心价值，必答

**答题框架：**

四道防线：

1. **提示词约束**：系统提示里明确写「只依据提供的资料回答，资料不足就说不知道，不要编造」。
2. **检索兜底**：如果检索结果的相关度太低，直接返回「知识库暂无相关内容」，不把无关片段喂给模型。我设了个阈值，字面重叠低于 4% 就丢弃。
3. **来源可查**：回答下面附 5 条来源片段，用户能点开看原文。这既是透明，也是一种约束——模型知道要对应得上。
4. **实测**：抽检时问「番茄叶片发黄有白虫」，模型判定为烟粉虱并给出方案，还主动补了一句「资料未提供稀释倍数，建议按产品标签」——没有编剂量。

**追问预警：**
- 「模型还是编了怎么办」→ 目前只能靠人工抽检发现。更严谨的做法是加一层「答案-来源一致性校验」，让另一个模型判断回答的每句话能否在片段里找到依据，我没做，这是可改进的点。

### A5. 你测过效果吗？指标多少？

**概率：85%** ｜ 区分「做过」和「想过」的关键题

**答题框架：**

测过，拆成三个指标，因为「准确率」对 RAG 是个含糊说法：

| 指标 | 结果 | 怎么测的 |
|---|---|---|
| 检索 Recall@5 | **88%** | 人工出 25 题，标注期望命中的文档，看 top-5 里有没有 |
| 检索 MRR | 0.741 | 第一个正确结果的平均倒数排名 |
| 回答要点覆盖 | **95%** | 10 题，标注 2–3 个关键要点，看回答有没有讲到 |
| 领域拦截准确率 | **100%** | 15 个农业问题 + 15 个非农问题 |

**关键细节**：出题时**不能照抄文档标题**。比如期望文档是《2024 年全国冬小麦春季田间管理技术意见》，问题要写成「小麦返青拔节期什么时候追肥」——直接写标题等于把答案关键词喂给检索器，测出来虚高。

**主动说局限**（这句很加分）：25 题的置信区间大约 ±12 个百分点，88% 和 80% 在统计上区分不开。要稳定结论得扩到 100 题以上。

**追问预警：**
- 「为什么 Recall@5 只有 88%，那 12% 呢」→ 3 题没命中，其中 2 题是召回了同类文档（比如问赤霉病，召回的是另一份病虫害方案，内容其实讲了），1 题是真实偏差。标题口径偏严，实际可用性比 88% 高——回答要点覆盖 95% 就是这个意思。

### A6. Agent 和 RAG 有什么区别？为什么要加 Agent？

**概率：85%** ｜ 项目亮点，也是简历上的关键词

**答题框架：**

**本质区别在控制流**：RAG 是固定管道，不管问什么都走「检索一次 → 生成」；Agent 是模型自主循环，先判断「我需要什么信息」，再决定调哪个工具、调几次。

**举个具体例子**（这个例子最有说服力）：
> 问「长春明天能打药吗」——RAG 只能检索到「避免高温时段施药」，但它不知道明天多少度。Agent 会先调气象工具拿到「明天有雨、风速 17m/s」，再判断「降雨冲刷药液、风速过大飘移」，最后给出「明天别打，后天转晴再说」。

**代价也要说**：Agent 每调一次工具就要多一次模型往返，延迟从 6.9 秒涨到 8.5 秒，成本也更高。所以我保留了两种模式——简单知识问答用 RAG 更快更稳，需要多步推理才切 Agent。

**关键认知**：Agent 不是取代 RAG，而是把 RAG 那条管道降级成工具箱里的一个工具（`search_knowledge`）。

**追问预警：**
- 「Agent 会不会死循环」→ 设了 5 轮上限，超了就强制让它总结现有结果。
- 「怎么保证它不乱调工具」→ 提示词里写了硬约束：涉及任何农技事实必须先检索，不能凭记忆答。改之前它问「玉米螟怎么防治」居然 0 次工具调用，直接凭记忆答了，这在 RAG 系统里是致命的——答案无法溯源。

### A7. 这个项目你遇到最大的困难是什么？

**概率：80%** ｜ 考的是解决问题的过程，不是困难本身

**答题框架**（选一个真实的，讲清「现象 → 排查 → 定位 → 修复」）：

**推荐讲这个：检索召回不准**

- **现象**：问「小麦越冬水什么时候浇」，召回的是「小麦播种技术」，答非所问。
- **排查**：先怀疑切片，把片段打出来看，发现内容完整、没有切断。再怀疑嵌入模型，换了个模型还是不准。最后把召回的 5 条和问题逐字对比，发现向量相似度高的片段，字面上跟问题几乎没重合。
- **定位**：纯向量检索在专有名词上会漂移——「越冬水」这个词在语义空间里可能靠近「冬季管理」，但用户要的是「越冬水」这个具体操作。
- **修复**：加了字面匹配信号。把问题和片段都拆成中文 2-gram（相邻两字），算覆盖率，然后按「向量相似度 0.65 + 字面覆盖 0.35」重排。
- **结果**：同一问题从「答非所问」变成「第 1 位命中」，整体 Recall@5 到 88%。

**为什么这个答案好**：有现象、有排查路径、有失败尝试（换模型没用）、有量化结果。比「困难是数据太少」这种空话强得多。

**追问预警：**
- 「0.65 和 0.35 怎么定的」→ 试出来的。字面权重再高会牺牲语义泛化（同义不同词就召不回），再低则专有名词还是漂。**（诚实说靠调参，别说做了网格搜索）**

## B 档 · 大概率会问（8 题）

### B1. 为什么用 Chroma，不用 FAISS 或 Milvus？

**概率：70%**

- **Chroma**：文件型，`pip install` 就能用，支持元数据过滤（我按 category 筛分类），自带持久化。适合单机、数据量万级以内。
- **FAISS**：性能强，但只是索引库，不管存储和元数据，要自己写一层封装。
- **Milvus**：分布式，适合亿级，但需要 Docker 部署，我这个场景是杀鸡用牛刀。

**一句话**：2270 个片段，Chroma 的检索延迟 20 毫秒（本地计算部分），完全够用。选型看规模，不选最先进的。

---

### B2. 向量维度为什么是 1024？

**概率：65%**

`text-embedding-v3` 支持 1024/768/512 等几档。选 1024 是因为：
- 维度越高语义表达越细，但存储和计算成本也涨。
- 1024 维在中文语义任务上是常见折中，2270 个片段占 35 MB，可接受。
- 维度是模型参数，换了模型维度就变——所以我的 collection 名带了 provider 和维度（`agri_dashscope_1024`），换模型自动隔离，不会串。

---

### B3. 多轮对话怎么实现的？

**概率：65%**

没有用 LangChain 的 Memory 组件，自己写了个简单的：

- 每个 session_id 存最近 5 轮问答（问 + 答）。
- 每次请求时，把这几轮拼进 messages 数组，放在 system prompt 之后、当前问题之前。
- 超过 20 轮就丢弃最早的，控制内存。

**验证过**：第一轮问「番茄叶片发黄有白虫」，第二轮只问「那用什么药」，模型能正确理解「那」指代番茄烟粉虱，给出对应药剂。

**追问**：「为什么只留 5 轮」→ 上下文太长会稀释当前问题，而且 token 成本线性增长。5 轮够覆盖大部分追问场景。

---

### B4. 流式输出怎么做的？

**概率：60%**

SSE（Server-Sent Events），不是 WebSocket。

- 后端用 FastAPI 的 `StreamingResponse`，每生成一个 token 就 `yield` 一条 `data: {...}`。
- 前端用 `EventSource` 接收，逐字追加到气泡里。
- 事件类型分了 `delta`（增量文本）、`sources`（来源）、`done`（结束）、`error`。

**为什么用 SSE 不用 WebSocket**：这是单向推送（服务端 → 客户端），SSE 更轻，基于 HTTP 不用额外协议，浏览器原生支持。

**实测**：首字延迟约 700 ms，用户感知比等 7 秒好很多。

---

### B5. 怎么保证非农问题不被回答？

**概率：60%**

两层：

1. **关键词拦截**（在模型之前）：农业词表命中就放行，非农词表命中就拦，都没有则看是否中文——非中文且无农业特征也拦。这层不花钱，0 次模型调用。
2. **提示词兜底**：系统提示里写「只回答农业相关问题」。

**实测**：15 个农业问题 + 15 个非农问题，准确率 100%。第一版只有 86.7%——「高铁」「笑话」「简历」「爬山」没进非农词表，漏放了 4 个。

**取舍**：宁可漏放也不错杀。误拦一个农技问题，用户直接走了；漏放一个非农问题，模型会说「我只能回答农业问题」，损失小。

---

### B6. Function Calling 具体怎么实现的？

**概率：55%**

一个循环，最多 5 轮：

1. 把用户问题 + 6 个工具的描述（JSON Schema）发给模型。
2. 模型返回 `tool_calls`（要调哪个工具、参数是什么），或者直接给答案。
3. 如果是 `tool_calls`：执行工具，把结果作为 `role: tool` 的消息塞回对话。
4. 回到第 1 步，模型看到工具结果后再判断。
5. 直到模型不再要求调工具，或者达到 5 轮上限。

**6 个工具**：知识库检索、农事日历、实时气象（接 Open-Meteo）、症状初诊、施肥量计算、农药稀释计算。

**注意**：工具里只有 `search_knowledge` 会调嵌入模型，其余 5 个是纯 Python 计算或 HTTP 请求，不碰大模型。

---

### B7. 数据量涨 10 倍怎么办？

**概率：50%** ｜ 考架构意识

- **向量库**：Chroma 到十万级会吃力，换 Milvus 或 Qdrant，接口层封装过，换实现成本不大。
- **入库**：现在是单线程顺序处理，改成多线程或异步批量。现在 598 篇用 2 分钟，6000 篇就是 20 分钟，可以接受但要优化。
- **检索**：加缓存（相同问题直接返回），加粗排（先按类别缩小范围再精排）。
- **切片**：语料大了要重新评估 chunk size，可能需要按文档类型分别设定。

---

### B8. 这个项目代码量多少？是你自己写的吗？

**概率：50%** ｜ ⚠️ **高风险题，见文末风险提示**

**建议答法**（诚实但不自贬）：

- 后端约 4200 行 Python，前端约 2800 行 Vue。
- 「架构设计、技术选型、参数调优和评测是我做的，具体代码实现过程中用了 AI 辅助——比如某个 LangChain API 的用法我会让它给我示例，但整体结构和每部分的逻辑是我定的。」
- 如果被追问某段代码：「这块的具体写法我需要看一下代码才能说准，但设计意图是……」（说意图，别硬编实现细节）

## C 档 · 深挖才会问（5 题）

### C1. 中文分词为什么不用 jieba？

**概率：35%**

我用的是 2-gram 而不是分词，原因是：
- 分词要先加载词典、处理未登录词（「稻飞虱」「蛴螬」这类专业词容易分错）。
- 2-gram 不需要词典，实现简单，对短查询的字面匹配效果够用。
- 代价是维度高、有噪声，但只用于重排信号，不影响主检索。

如果要做语义级的相似度，还是得上分词或直接用嵌入模型。

---

### C2. 有没有考虑用 Rerank 模型？

**概率：30%**

考虑过，没用。原因：
- 主流 rerank（如 bge-reranker）是本地模型，要下载几百 MB，还要推理，跟我「笔记本轻量运行」的定位冲突。
- 我现在用 2-gram 覆盖做重排，效果够（Recall@5 88%），成本几乎为零。
- 如果语料涨到十万级、精度要求更高，会考虑加 rerank——它是「检索召回后精排」的标准做法。

---

### C3. PDF 和表格怎么处理的？

**概率：25%**

- PDF 用 PyPDFLoader，按页提取文本。
- 表格是弱项——PDF 里的表格提取出来会变成一堆没有结构的文字，行列关系丢失。目前没做表格结构化，是已知缺陷。
- CSV 直接按行读。

---

### C4. 怎么做异常处理的？

**概率：20%**

- 接口层：统一异常处理中间件，参数校验失败返回 422，业务异常返回 500 并带错误码。
- 模型调用：超时和限流都会 catch，返回友好提示而不是堆栈。
- 记录写入：`history.add` 内部吞掉异常只记日志——记录失败不应该中断问答主流程。
- 降级：没有 API Key 时自动切 Mock 模式，链路能跑通，只是回答是占位文本。

---

### C5. 如果让你重做，会改什么？

**概率：20%** ｜ 考反思能力

三个：
1. **评测集太小**：25 题置信区间 ±12 个百分点，应该一开始就建 100 题以上的测试集，边开发边跑。
2. **没有 CI**：43 项自测是手动跑的，应该配 GitHub Actions，每次提交自动跑。
3. **语料质量把关不够**：现在靠关键词规则过滤新闻稿，还是漏了一些（比如「全国累计收购小麦超9000万吨」这种），应该加一道人工抽检或模型判别。

## ⚠️ 风险提示（重要）

这一节不写给面试官看，写给你自己。

### 1. 最大的风险：答不上实现细节

这个项目的代码是 AI 辅助生成的（大部分逻辑由 AI 写出）。面试官如果盯着某一行问「这里为什么这么写」，你很可能答不上来。

**应对策略：**

- **主动控制话题**。答 A1 时就把话题往「设计取舍」和「评测数据」上引——这两块你能讲，代码细节你讲不了。
- **准备好「我不知道」的说法**：「这块具体实现我需要翻代码确认，但我记得设计意图是……」。说意图比编实现安全一百倍。
- **提前跑一遍项目**。至少把 `python start.py` 跑起来，六个页面点一遍，问几个问题，看看返回什么。手上有真实操作经验，说话底气完全不同。

### 2. 两个 RAG 项目的时间线

简历上有两个 RAG 项目：2026.06 的「农业智能问答系统」（课程实习）和 2026.10 的「农业智能问答助手」（个人项目）。面试官会问「为什么半年做两个差不多的」。

**准备好的说法**：「课程实习那版是 Streamlit + 本地向量模型，功能比较单薄，只能问答；后来用 FastAPI + Vue 重做了一版，加了知识库管理、历史记录、评测体系和 Agent 工具调用，算是把工程化补齐了。」

这个说法是真实的，也解释了技术栈升级。

### 3. 简历上的数字都能被验证

598 篇、2270 片段、Recall@5 88%、MRR 0.741、拦截 100%、43 项自测——这些都在 `docs/eval-report.json` 和工程文档里。如果面试官要求看，你能拿出来。

**这是你的优势**：大部分应届生简历上的数字是编的，你的能查。

### 4. 别主动提「AI 写的」

如果没被直接问，不用主动说。但如果被问到「这段代码你怎么想的」而你答不上来，不要硬编——说「需要看代码确认」比编一个错误的解释强。

**底线**：可以不说，但不能撒谎说「每一行都是我写的」。这是能查证的事（代码风格、注释习惯、Git 提交记录）。
