# 第一部分 项目计划书

## 1.1 项目概述

本项目面向农业农技咨询场景，结合大语言模型与检索增强生成（RAG）技术，开发一款农业垂直领域 AI 对话助手。系统覆盖农业语料处理、知识库构建、智能问答、多轮对话、记录管理与可视化交互的全流程，并在 RAG 基础上进一步升级为具备工具调用能力的 Agent 系统。

全部开发、运行、测试工作仅依托学生个人笔记本电脑完成，不使用服务器、独立显卡与集群资源，所有组件均为文件型、嵌入式、轻量级。

## 1.2 项目目标

| 序号 | 目标 | 达成标志 |
|---|---|---|
| 1 | 建成轻量化农业语料库 | 清洗后不少于 500 篇，四大类归档 |
| 2 | 实现文件型向量库 | Chroma 本地持久化，无独立服务进程 |
| 3 | 实现农业 RAG 问答 | 检索命中 + 云端生成，答案贴合农技场景 |
| 4 | 实现领域边界控制 | 非农问题拦截率 100%，输出标准引导语 |
| 5 | 实现多轮对话 | 上下文连贯，记忆限定最近 5 轮 |
| 6 | 实现记录管理 | 自动持久化、条件查询、统计、CSV 导出 |
| 7 | 实现可视化界面 | 六个页面，单命令启动 |
| 8 | 升级为 Agent 系统 | 六类工具，Function Calling 多步推理 |

## 1.3 范围界定

**包含**：语料抓取与清洗、切片与向量化、检索与生成、多轮记忆、记录管理、Web 界面、Agent 工具集。

**不包含**：复杂实体抽取、知识图谱构建、本地大模型推理、模型微调、多用户权限体系、分布式部署。这些内容与「笔记本单机、低资源」的核心约束冲突，明确排除。

## 1.6 风险与应对

| 风险 | 影响 | 应对措施 |
|---|---|---|
| 大模型 API 额度不足或限流 | 问答不可用 | 支持百炼/智谱双提供方切换；无密钥时降级 Mock 模式保证链路可演示 |

# 第二部分 需求规格说明书

## 2.1 项目背景

农业生产全流程中，种植户、养殖户与基层农技员会产生大量技术疑问，但权威农技资料分散在官网、PDF、科普文章中，检索成本高、专业门槛高。通用大模型虽能对话，但缺乏农业领域知识约束，容易给出不适用的建议。

本系统通过 RAG 技术，把权威农技资料转化为可检索的知识库，让模型「基于资料回答」，同时通过领域拦截保证回答不越界。

# 第三部分 概要设计说明书

## 3.1 总体架构

系统采用前后端分离架构，后端提供 REST + SSE 接口，前端为 Vue3 单页应用，构建产物由后端静态托管，实现单端口、单命令启动。

```
┌─────────────────────────────────────────────┐
│              浏览器（Vue3 SPA）              │
│  首页 / 问答 / 知识库 / 向量库 / 历史 / 设置  │
└──────────────────┬──────────────────────────┘
                   │ HTTP + SSE
┌──────────────────▼──────────────────────────┐
│              FastAPI 应用层                  │
│  chat │ kb │ vector │ history │ settings │ agent │
└──────────────────┬──────────────────────────┘
                   │
┌──────────────────▼──────────────────────────┐
│                核心服务层                    │
│  RAG 编排 │ 入库编排 │ 会话记忆 │ 记录管理    │
│  Agent 执行器（Function Calling 循环）       │
└──────────────────┬──────────────────────────┘
                   │
┌──────────────────▼──────────────────────────┐
│                基础能力层                    │
│ 加载 │ 清洗 │ 切片 │ 嵌入 │ 向量库 │ 领域拦截 │
└──────────────────┬──────────────────────────┘
                   │
┌──────────────────▼──────────────────────────┐
│              存储与外部依赖                  │
│ 语料文件 │ Chroma │ JSONL │ 云端 LLM/Embedding │
└─────────────────────────────────────────────┘
```

## 3.3 数据设计

### 3.3.1 语料文件

以文件系统组织，目录即分类：

```
data/corpus/
├── planting/    # 种植技术
├── pest/        # 病虫害防治
├── breeding/    # 养殖技术
└── general/     # 通用农技
```

单篇格式（带元信息头，便于溯源）：

```
标题：2026年小麦秋冬种技术意见
栏目：农事指导
日期：2026-09-15
来源：http://www.agri.cn/sc/nszd/...
----------------------------------------
（正文）
```

### 3.3.2 向量库

Chroma 持久化于 `data/chroma/`，collection 命名规则：

```
agri_{embedding_provider}_{dim}
```

按提供方与维度隔离，避免切换嵌入模型后维度冲突。

### 3.3.3 对话记录

JSONL 逐行追加，单行结构：

```json
{
  "id": "a1b2c3d4e5f6",
  "session_id": "9f8e7d6c5b4a",
  "question": "小麦越冬水什么时候浇",
  "answer": "……",
  "ts": 1793001615.13,
  "datetime": "2026-10-26 16:00:15",
  "latency_ms": 1240,
  "mode": "rag",
  "sources": [{"title": "...", "category": "种植技术"}],
  "blocked": false,
  "tool_calls": []

```

## 3.4 关键接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/chat/ask` | 非流式问答，`mode` 可选 rag/agent |
| GET | `/api/chat/stream` | SSE 流式问答，事件 sources/delta/tool/done |
| POST | `/api/vector/build` | 启动后台入库任务 |
| GET | `/api/vector/progress` | 轮询入库进度 |
| POST | `/api/history/list` | 条件分页查询 |
| GET | `/api/history/export` | 导出 CSV（UTF-8 BOM） |
| POST | `/api/agent/ask` | Agent 问答，返回工具轨迹 |

## 3.5 关键技术决策

**决策一：文件型 Chroma 而非向量数据库服务**
文档明确要求无独立服务、无端口占用。Chroma embedded 模式把索引落在本地目录，随项目复制即可迁移，符合单机部署约束。

**决策二：清洗置于切片之前**
PDF 与网页文本常带页眉页脚、导航、版权声明。若先切片，噪声会与正文混在同一片段被误召回。故顺序为「加载 → 清洗去重 → 切片」。

**决策三：领域拦截采用「白名单优先 + 模糊放行」**
纯黑名单会误杀生僻作物名。策略是：命中农业词直接放行；命中非农词且无农业词才拦截；两者都未命中时放行，交给 Prompt 约束。宁可少拦，不可错杀。

**决策四：Mock 降级而非硬报错**
无密钥时若直接抛错，整条链路无法演示与验收。Mock 嵌入用字符 bigram 哈希生成确定性向量，能真实走完入库、检索、排序、Prompt 组装全流程。

**决策五：Agent 与 RAG 共用底层**
两者复用同一套知识库、记忆与记录模块，差异仅在「检索是一次固定动作还是模型可选动作」。因此切换成本为零，且历史记录格式统一。

## 3.6 异常处理设计

| 异常场景 | 处理方式 |
|---|---|
| 语料目录为空 | 入库任务直接结束并提示「语料目录为空」 |
| 单文件解析失败 | 跳过并计入 skipped，不中断整批 |
| 嵌入接口限流 | 指数退避重试 3 次，仍失败则记录并继续后续批次 |
| 向量库未初始化 | 问答返回「请先完成入库」引导语 |
| 模型调用失败 | 返回错误摘要，不抛出 500 |
| 非农问题 | 返回标准拒答话术，并记入历史（blocked=true） |
| 工具执行异常 | 错误回传给模型，由模型决定是否换工具或说明原因 |

## 5.3.2 量化评测

前面 5.3.1 是定性观察，本节给出可复现的量化指标。脚本：`scripts/evaluate.py`，结果：`docs/eval-report.json`。

### 为什么拆成三个指标

对 RAG 系统说「准确率 85%」是没有意义的——它把检索、生成、拦截三个独立环节混成一个数。任一环节出问题都会拉低整体，但修复手段完全不同。因此分别度量：

| 指标 | 衡量什么 | 出问题时该改哪 |
|---|---|---|
| 检索命中率 Recall@k | 该找的资料有没有被找出来 | 切片策略、嵌入模型、混合检索权重 |
| 回答要点覆盖率 | 生成内容有没有讲到关键点 | 提示词、top_k、上下文组织 |
| 领域拦截准确率 | 该拦的有没有拦、该放的有没有放 | 关键词表、判定规则 |

### 测试集构造

| 项目 | 规模 | 构造方式 |
|---|---|---|
| 检索评测集 | 25 题 | 人工编写，覆盖种植 10 / 病虫害 8 / 养殖 4 / 通用 3 |
| 回答评测集 | 10 题 | 从检索集抽取，覆盖四类 |
| 拦截评测集 | 30 题 | 农业问题 15（应放行）+ 非农问题 15（应拦截） |

构造原则：

1. **问题用农户口吻，不照抄文档标题**。例如期望文档是《2024 年全国冬小麦春季田间管理技术意见》，问题写成「小麦返青拔节期什么时候追肥，施多少」，而不是「冬小麦春季田间管理技术意见」——后者等于把答案关键词直接喂给检索器。
2. **期望文档与要点依据语料实际内容确定**，先确认文档存在、内容确实覆盖该主题，再标注。
3. 一个问题可能有多个合理文档（如「玉米什么时候追肥」），给出多个期望关键词，命中任一即算对。

### 未命中案例分析

3 题未在 top-5 命中期望文档：

| 编号 | 问题 | 实际召回 | 判断 |
|---|---|---|---|

| R23 | 秋粮遇到灾害怎么减灾保丰收 | 2024年全国秋粮「一喷多促」技术意见 | 语义相关但非目标文档 |

前两例说明**标题口径偏严**：召回的文档虽然标题不含「小麦」「设施蔬菜」，但内容确实是相关的病虫害防控与蔬菜生产方案。后一例是真实的召回偏差——「一喷多促」是增产措施，与「防灾减灾」不完全等价。

### 一个值得注意的发现

**检索标题命中 88%，但回答要点覆盖 95%。**

端到端效果优于单文档命中率，原因在于 RAG 不依赖单一文档：即使 top-1 不是期望文档，多个片段的拼合仍能覆盖关键信息。R13、R18 两题检索「未命中」，回答要点却都拿到了 100%——召回的《2025年粮食作物重大病虫害防控技术方案》《蔬菜冬季生产技术指导意见》里确实讲了赤霉病和灰霉病。

这说明：**单看检索命中率会低估系统实际可用性**，但它仍是必要的诊断指标——因为它直接指向可优化的环节。

### 局限性

必须说明，避免把上面数字当成绝对结论：

1. **样本量偏小**。25 题的 95% 置信区间约 ±12 个百分点，88% 与 80% 在统计上不可区分。要得出稳定结论需扩充到 100 题以上。
2. **标注有主观性**。「哪些文档算正确」由人工判定，换个人标注结果可能不同。
3. **要点覆盖是弱指标**。它只检查回答里有没有出现关键词，不判断表述是否准确、是否自相矛盾。可能出现「提到了但说错了」仍得分的情况。
4. **未覆盖拒答场景**。真实使用中用户会问知识库没有的内容，系统应当承认「不知道」而非编造，本次评测未设计此类用例。

后续改进方向：扩充到 100+ 题、引入第二人独立标注、增加「无答案问题」测试集衡量拒答准确率。

| PT-05 | Agent 链路 | 平均 7363.6 ms（最大 8098 ms） | — | 优化后较首版下降约 1.1 秒 |
| PT-06 | 内存占用 | 236.4 MB（含 4 个 python 进程） | ≤ 800 MB | 达标 |
| PT-07 | 连续运行 | 持续运行 30 分钟无崩溃、无内存增长 | 无崩溃 | 达标 |
| PT-08 | 知识库列表 | 首次 0.7 秒（预热后），命中缓存 7 ms | — | 达标 |

**向量库规模**：2270 片段 · 35.13 MB · 1024 维。

### 5.4.2 Mock 模式（无密钥降级）

| 编号 | 指标 | 实测值 |
|---|---|---|
| PT-08 | 检索延迟 | 平均 20.0 ms，P95 28.0 ms |
| PT-09 | 问答链路 | 平均 27.2 ms |
| PT-10 | 内存占用 | 228 MB |

### 5.4.3 结论

- **检索延迟**：真实模式 195 ms，其中绝大部分是嵌入接口的网络往返（本地向量计算仅 20 ms）。
- **问答延迟**：6.9 秒主要消耗在云端模型生成，属正常范围。流式模式下首字延迟约 700 ms，用户感知良好。
- **Agent 延迟**：比 RAG 高约 1.6 秒，符合「多一次模型往返」的预期，未出现失控重试。
- 两种模式内存占用均低于 250 MB，远优于 800 MB 的约束。

> Mock 模式用于无密钥时的链路验证与离线演示，其数值反映系统自身开销，
> 不含网络往返；真实模式数值更贴近实际使用体验。

## 5.6 测试结论

系统七大功能模块全部实现并通过测试，核心逻辑自测 43 项全部通过，接口测试 28 项全部通过，性能指标满足「普通笔记本单机运行」约束。

量化评测结果：**检索 Recall@5 = 88.0%（MRR 0.741）、回答要点覆盖 95.0%、领域拦截准确率 100.0%**。真实模型模式下问答质量抽检 5 例全部符合预期，Agent 的多工具协同与实时数据接入均正常工作。

系统达到验收标准，可用于实习项目答辩与演示。

遗留事项：
1. 语料以种植业为主（503 篇），养殖类仅 26 篇，畜禽养殖问题的召回覆盖不足，可通过补充 `corpus/breeding/` 语料改善。
2. 语料分类依赖关键词规则，长尾作物可能存在误分类，可通过扩充词表持续优化。
3. Agent 单次提问上限 5 轮工具调用，复杂多跳问题可能被截断，后续可考虑分级限步或引入任务规划。
4. 量化评测样本量 25 题，置信区间约 ±12 个百分点，需扩充到 100+ 题才能得出稳定结论。
5. 语料中仍混有少量新闻类文本（如「全国累计收购小麦超9000万吨」），关键词规则无法完全识别，建议入库前人工抽检。

# 第六部分 用户使用手册

## 6.1 环境准备

**必需**：Python 3.8 ~ 3.10（推荐 3.10）
**可选**：Node.js 18+（仅在需要重新构建前端时使用）

验证 Python：

```bash
python --version
```

## 6.2 安装

### 6.2.1 解压与创建虚拟环境

```bash
cd agri-rag-qa
python -m venv .venv

# Windows
.venv\Scripts\activate
# macOS / Linux
source .venv/bin/activate
```

### 6.2.2 安装依赖

```bash
pip install -r backend/requirements.txt
```

国内网络较慢时可加镜像：

```bash
pip install -r backend/requirements.txt -i https://pypi.tuna.tsinghua.edu.cn/simple
```

### 6.2.3 配置模型密钥

复制 `.env.example` 为 `.env`，编辑：

```ini
DASHSCOPE_API_KEY=sk-你的密钥
LLM_PROVIDER=dashscope
LLM_MODEL=qwen-plus
EMBEDDING_PROVIDER=dashscope
EMBEDDING_MODEL=text-embedding-v3
```

密钥获取：登录 <https://bailian.console.aliyun.com/> → API-KEY 管理 → 创建。

> 不填密钥也可启动，系统进入 Mock 演示模式，功能链路完整但回答为占位文本。

## 6.3 准备语料

**方式一：自动抓取**（需联网）

```bash
python scripts/crawl_corpus.py
```

默认从中国农业农村信息网抓取农事指导、生产动态、智慧农业等栏目，约 500~600 篇。

**方式二：手动导入**

把文档放入对应目录：

```
backend/data/corpus/planting/    种植技术
backend/data/corpus/pest/        病虫害防治
backend/data/corpus/breeding/    养殖技术
backend/data/corpus/general/     通用农技
```

支持 `.txt` `.md` `.pdf` `.csv`，单文件不超过 20MB。

**方式三：页面导入**

启动后在「知识库管理」页拖拽上传，选择归档分类。

## 6.4 启动系统

```bash
python start.py
```

看到以下输出即启动成功：

```
服务地址： http://127.0.0.1:8000
接口文档： http://127.0.0.1:8000/docs
```

浏览器打开 <http://127.0.0.1:8000>。

指定端口：`python start.py --port 8080`
开发热重载：`python start.py --reload`

## 6.5 首次使用：构建向量库

**这是必须完成的一步**，否则问答无法检索知识。

1. 左侧点击「向量库构建」
2. 保持默认参数（切片 500 / 重叠 50）
3. 入库模式选「清空重建」
4. 点击「开始构建向量库」
5. 等待进度到 100%，页面显示「入库完成：N 篇有效文档，M 个片段」

首次构建约 1~3 分钟（取决于语料量与嵌入接口速度）。

## 6.6 功能操作

### 6.6.1 智能问答

1. 左侧点击「智能问答」
2. 输入问题，按 Enter 发送（Shift+Enter 换行）
3. 回答下方点击「参考 N 条知识库片段」可展开溯源
4. 点击「清空会话」释放上下文记忆

**模式切换**：
- **RAG 模式**：检索一次 + 生成一次，快且可控
- **Agent 模式**：模型自主调用工具，适合需要多步推理的问题

**提问技巧**：
- 说清作物/畜禽 + 部位 + 症状，例如「番茄下部叶片发黄，叶背有白色小虫」
- 定量问题给出目标，例如「亩产 500 公斤小麦要施多少尿素」
- 时间问题给出地区，例如「长春现在能给小叶菜打药吗」

## 6.7 常见问题

**Q1：启动后首页显示「前端尚未构建」**
```bash
cd frontend && npm install && npm run build
```
构建完成后刷新页面。

**Q2：问答提示「知识库尚未初始化」**
到「向量库构建」页执行一次构建。

**Q3：提示「未配置 API Key」**
在 `.env` 中填入 `DASHSCOPE_API_KEY`，或到「系统设置」页填写后重启。

**Q4：切换嵌入模型后检索报错**
不同模型维度不同，必须重新构建向量库。

**Q5：入库很慢**
取决于嵌入接口速度。可先只处理一个分类验证，或减少语料量。

**Q6：端口被占用**
`python start.py --port 8080`

**Q7：想彻底重置**
删除 `backend/data/chroma/` 与 `backend/data/records/` 后重启。

**Q8：Agent 模式没有工具调用**
检查是否处于 Mock 模式（无密钥）。Agent 需要真实模型支持 Function Calling。
